# API

## Status

Frontend menyediakan HTTP client dan service CRUD di `src/services/api/` untuk backend Laravel 12+ dengan MySQL 8+. Service ini belum menjadi sumber data runtime karena backend belum tersedia; prototype masih menggunakan facade mock dan LocalStorage.

HTTP client telah menangani:

- base URL dari `VITE_API_BASE_URL`
- bearer token atau Sanctum cookie
- CSRF cookie opsional
- timeout dan pembatalan request
- normalisasi Laravel Resource dan pagination
- validation error Laravel
- upload `FormData`
- download Blob untuk PDF/Excel/CSV

Kontrak detail backend tersedia di [[LARAVEL_API_SPEC]].

## Addendum 22 Oktober 2026 - Versi Jadwal dan CMS

- Ketiga endpoint reschedule pasien/admin/psikolog wajib menerima `expected_version` integer dari resource saat form dibuka. Di transaction, lock appointment, periksa versi dan status/ownership terbaru, lalu periksa kapasitas slot. Jika versi berbeda, kembalikan `409` dengan kode `SCHEDULE_VERSION_CONFLICT` tanpa mengubah jadwal/ledger; FE harus membaca ulang dan meminta pemilihan ulang.
- Simpan `appointments.schedule_version` integer non-negatif, mulai 0 dan bertambah pada setiap reschedule sukses. Resource appointment pasien/psikolog/admin menyertakan `scheduleVersion` sesuai entity frontend. Prototype legacy tanpa field memakai panjang `rescheduleHistory`; backend harus melakukan backfill, bukan mengandalkan fallback client.
- `GET /cms/landing` hanya konten publik, tanpa `bankName`, `bankAccountNumber`, `bankAccountHolder`, atau `qrisImageUrl`. Owner membaca konfigurasi lengkap lewat `GET /psychologist/cms/landing`; seluruh `PUT /cms/:section` dan upload aset hanya psikolog/pengelola, bukan admin.
- Rekening penerima ditentukan server dan disnapshot pada hold. Response hold milik pasien menambahkan `payment_channel_detail` dan `account_holder` untuk transfer bila diizinkan alur consent. Jangan mempercayai rekening dari request pasien. Edit CMS tidak mengubah instruksi hold lama.
- Snapshot appointment baru memakai lokasi praktik yang berlaku saat dibuat; edit alamat tidak memindahkan jadwal lama. QRIS CMS merupakan referensi kasir admin, bukan aktivasi payment gateway.
- Detail field/editor dan yang masih statis ada di [[CMS_AUDIT]]. Service dan field ini masih kontrak; runtime belum memakai backend.

## Konvensi

- Prefix endpoint: `/api/v1`.
- Semua endpoint privat wajib memakai authentication dan policy berdasarkan role/kepemilikan data.
- Payload request memakai `snake_case`; API Resource harus mengembalikan kontrak entity yang disepakati frontend.
- Error validasi memakai status `422` dengan `{ message, errors }`.
- Operasi booking, pembayaran, dan sesi lanjutan wajib idempotent dan menggunakan database transaction.
- Response admin tidak boleh mengekspos harga paket, target tagihan, atau nominal pelunasan yang sudah dicatat.

## Endpoint Appointment dan Pembayaran

### Kontrak Pengaman Booking dan Kas (21 Oktober 2026)

- `POST /slot-holds`: patient, body `psychologist_id, package_id, date, start_time, end_time, idempotency_key`. Server menghitung end_time/durasi dan quote, memeriksa H+1, ownership, aturan praktik, kuota, serta overlap dalam transaction dengan row lock kapasitas per psikolog/tanggal.
- `GET /slot-holds/:id`: hanya pemilik/role berwenang; response `id, status, psychologist_id, package_id, date, start_time, end_time, expires_at, server_time, package_version, total_amount, dp_amount`. Status kontrak `HELD|PAYMENT_REVIEW|CONVERTED|EXPIRED|RELEASED`; sumber waktu/expiry dari server.
- `POST /slot-holds/:id/release`: pelepasan hold belum terkonversi oleh pemilik, idempotent. Jangan melepas booking/pembayaran terverifikasi melalui endpoint ini.
- Target `POST /appointments` wajib menyertakan `slot_hold_id` dan `expected_total_amount`. Expected total hanya guard persetujuan, bukan harga otoritatif. Server memvalidasi ownership, masa berlaku, versi paket, dan nominal hasil kalkulasinya; `409` bila quote berubah/hold tidak valid, tanpa menagih ulang otomatis.
- Runtime mock sudah memakai hold lokal sebelum rekening, dengan default konfigurasi 15 menit; ini bukan TTL produksi final. Setelah expiry/quote berubah, bukti tersimpan pada kasus OPEN tanpa transfer kedua. Hold server tetap harus mengganti mekanisme lokal saat integrasi Laravel; jangan mempercayai waktu/kapasitas browser untuk produksi.
- Walk-in wajib `initial_payment_amount` dan `payment_phase=DP|FULL`. Server memvalidasi nominal aktual sesuai fase, menyimpan ledger dan konfirmasi atomik; FULL awal psikoterapi ditolak. Response admin tidak mengembalikan nominal.
- Verifikasi DP menerima `received_date`; pembayaran lanjutan wajib `received_date` (`YYYY-MM-DD`, bukan masa depan, WIB). Walk-in/pencocokan pembayaran menerima `received_date` agar penerimaan lama tidak dipindah ke hari input. `recorded_at/verified_at` berasal dari waktu server. Tanggal tidak boleh diubah ketika reconfirm reschedule.
- `GET /payment-reconciliations`: pasien hanya kasus miliknya; admin/pengelola sesuai kewenangan. Resource berisi identitas operasional, hold, status, waktu, serta private signed proof URL; tidak mengembalikan nominal tersimpan kepada admin.
- `POST /payment-reconciliations`: multipart `slot_hold_id, transfer_sender_name, payment_proof, idempotency_key`. Validasi pemilik hold dan file privat, unik/idempotent per hold. Kasus belum berarti uang terverifikasi atau appointment confirmed. Tidak ada endpoint permintaan unggah ulang bukti.
- `POST /admin/appointments/walk-in` menerima `reconciliation_id` opsional untuk booking pengganti. Kasus wajib OPEN dan pasien sesuai; lock kasus/kapasitas/ledger dalam transaction. Gunakan bukti sebelumnya, input nominal/tanggal aktual secara write-only, ikat appointment, dan jangan membuat pembayaran kedua. Status kasus BOOKED menyimpan appointmentId; konfirmasi/receipt mengikuti verifikasi standar.
- `/finance/transactions` (hanya psikolog/pengelola) mengembalikan baris event penerimaan, bukan satu agregat per appointment; filter tanggal mengikuti `received_at`. Mapping frontend memakai `CashInReportRow` termasuk `sourceAppointmentId`, `cashInAmount`, `cashInKind`, `cashInOccurredAt`, dan `cashInDateEstimated`. Agregat dan export wajib memakai event yang sama.
- Pembaruan schedule wajib menolak bentrok dengan appointment/hold aktif dan mengembalikan booking terdampak. Semua jalur booking/hold/reschedule/perubahan jadwal memakai urutan lock yang konsisten; jalur ledger/session memakai lock plan serta idempotency.

Endpoint `POST /admin/appointments/:id/verify-payment` wajib memeriksa status serta keberadaan bukti dan mengubah pembayaran `DP_PENDING_VERIFICATION -> DP_PAID/PAID` sekaligus booking `PENDING -> CONFIRMED` dalam satu transaction. FULL walk-in menunggu verifikasi seperti pembayaran awal lainnya dan baru menjadi PAID setelah jumlah aktual diverifikasi; paket gratis tidak memerlukan penerimaan uang. Response menyertakan audit verifikasi. Konfirmasi ulang reschedule memakai endpoint tersendiri dan hanya menerima pembayaran yang sudah terverifikasi; audit DP awal dipertahankan. Tidak ada endpoint permintaan unggah ulang bukti.

`POST /appointments` menerima `pre_test_id`, `consent_given`, `consent_version`, `privacy_version`, dan bukti `payment_proof` dalam multipart untuk layanan berbayar. Dalam satu transaction, backend mengikat draft pre-test, mencatat consent dengan waktu/IP/user agent server, memvalidasi slot, dan membuat booking. Upload bukti menjadi bagian create; tidak ada endpoint terpisah untuk mengganti bukti booking.

Seluruh response admin memakai `AdminAppointment`/`AdminAppointmentReceipt` dengan allowlist field administratif. Jangan mengembalikan `Appointment` penuh, snapshot pre-test/consent, subtotal/diskon, nominal DP/tagihan, saldo, atau ledger. `listForAdmin` dan `getForAdmin` memakai path list/detail yang sama, tetapi server wajib memilih Resource berdasarkan role.

Pembayaran lanjutan menerima `purpose=CONSULTATION|CANCELLATION_SETTLEMENT`. Purpose penghentian mengizinkan pencatatan sebelum sesi pertama; tetap write-only. Endpoint cancel/discontinue hanya psikolog: wajib saldo nol dan `PAID`, membatalkan seluruh sisa jadwal dalam rencana, menyimpan audit, serta mempertahankan histori completed dan uang masuk. Tidak ada refund otomatis.

Reschedule oleh psikolog menerima payload tanggal/jam/alasan yang sama dengan reschedule biasa. Policy wajib memeriksa psikolog penanggung jawab, status/rencana aktif, H+1 WIB, durasi, kuota, serta overlap dalam transaction. `NO_SHOW` hanya dapat dipulihkan manual oleh psikolog, bukan admin/pasien; pembayaran awal harus sudah terverifikasi. Pindahkan appointment yang sama ke `CONFIRMED`, simpan event status dan jadwal, tanpa mengubah nomor sesi, DP, cicilan, saldo, bukti, atau tanggal kas. Tolak jika sudah ada sesi lanjutan atau sesi aktif lain dalam rencana. Tidak ada auto-cancel atau DP kedua.

Admin hanya dapat memverifikasi pembayaran sekaligus mengonfirmasi booking, mencatat uang masuk satu arah, membantu reschedule, serta mencetak receipt administratif. Admin tidak dapat membaca harga paket, target saldo, atau nominal yang sudah disimpan. Complete, no-show, cancel, penjadwalan sesi ke-2 sampai ke-4, dan discontinue hanya milik psikolog. Tidak ada aksi tambah sesi di luar empat sesi awal.

Backend wajib mengabaikan nominal subtotal, diskon, total, dan DP dari client. Subtotal/diskon/total dihitung ulang dari paket aktif, sedangkan DP ditetapkan server sebesar Rp100.000 atau sebesar total akhir jika total akhir lebih kecil. Semua booking, termasuk walk-in admin, wajib memilih tanggal minimal H+1. Walk-in admin boleh membuat pasien baru tanpa pre-test awal, tetapi tetap wajib menolak paket nonaktif, durasi tidak sesuai, hari libur, kuota penuh, dan overlap slot.

## Endpoint Paket Berjalan

- `GET /treatment-plans`
- `GET /treatment-plans/:id`
- `POST /treatment-plans/:id/sessions`
- `PATCH /treatment-plans/:id/discontinue`

Appointment sesi berikutnya dibuat bertahap. Endpoint penjadwalan hanya menerima treatment plan dengan pembayaran awal `DP_PAID/PAID` dan sesi terakhir `COMPLETED`, mewajibkan tanggal minimal H+1, menerima idempotency key, menolak sesi aktif/nomor sesi duplikat, mempertahankan durasi paket, serta memvalidasi jam kerja, hari libur, kuota, dan overlap dalam transaction.

Tidak ada endpoint penambahan sesi pada plan. Setelah sesi keempat selesai, pasien membuat booking psikoterapi baru melalui `POST /appointments` dengan tarif per sesi saat booking baru, kode booking/DP/ledger baru, dan pemeriksaan slot minimal H+1. Penomoran sesi klinis berkelanjutan berada di rekam medis di luar sistem booking.

Pembayaran setelah DP dicatat sebagai banyak payment record, bukan menimpa satu kolom `final_payment_amount`. Nominal parsial tidak membuat status `PAID`; status baru `PAID` ketika saldo proyeksi empat sesi nol. Invoice dan laporan membaca ledger transaksi. Jadwal sesi ke-2 sampai ke-4 dibuat lewat endpoint `/sessions` satu per satu oleh psikolog.
